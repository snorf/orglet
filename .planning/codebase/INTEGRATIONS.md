# External Integrations

**Analysis Date:** 2026-11-03

## APIs & External Services

**Salesforce Emulation (What This Project Provides):**

orglet is a single-tenant Salesforce emulator that exposes Salesforce-compatible HTTP surfaces to existing Salesforce clients. It is not an integration with Salesforce; it *replaces* Salesforce locally.

- **REST API** - `/services/data/*` endpoints (describe, query, CRUD sobjects, composite, limits, bulk)
  - Response envelopes, error shapes, field types match Salesforce exactly
  - OAuth 2 token endpoint: `/services/oauth2/token` (grant_type: authorization_code, refresh_token, client_credentials, password)
  
- **SOAP API** - `/services/Soap/c/<version>` (Enterprise WSDL subset)
  - Login endpoint supporting username/password + security token (tolerated, not enforced)
  - Basic session-based authentication mirroring Salesforce behavior

- **Bulk API 2.0** - `/services/data/jobs/ingest` and related job/result endpoints
  - Job lifecycle: Open → InProgress → Completed/Failed
  - Record insertion via CSV with jobId tracking

- **Query Execution** - SOQL queries against the org's schema
  - Translated to parameterized PostgreSQL by `packages/soql/src/compile.ts`
  - Result shaping matches Salesforce (field order, null handling, date/time formats)

- **Object Describe** - sObject metadata API (`describe`, `describeSObjects`)
  - Returns Salesforce-standard field descriptors (type, length, picklistValues, referenceTo, etc.)

- **Login & Sessions** - OAuth token generation and bearer token validation
  - Emulates Salesforce user authentication (permissive mode for dev, list mode for list-based credentials)
  - Session store in-memory (per-server instance)

## Data Storage

**Databases:**

Primary (production-like):
- **PostgreSQL 16** - single source of truth for all record data, org schema (DDL), Postgres-specific internal state
  - Connection: `$ORGLET_DATABASE_URL` or default `postgres://orglet:orglet@localhost:5433/orglet` (docker-compose)
  - Client: `pg` npm package (no ORM; raw SQL generated by `packages/soql` and `packages/schema`)
  - Driver integration: `packages/schema/src/db.ts` wraps `pg.Pool` and configures type parsers for Salesforce-compatible date/decimal rendering
  - DDL generated by: `packages/schema/src/ddl.ts` (creates tables, columns, constraints, indexes per OrgSchema)
  - Schema management: `packages/schema/src/migrate.ts` (diff, plan, apply migrations)

Test/Ephemeral:
- **pglite (in-memory SQLite-style Postgres)** - when `$ORGLET_DATABASE_URL` is unset (default for local tests)
  - Package: `@electric-sql/pglite` 0.5.8 (root devDependency)
  - Wrapper: `@electric-sql/pglite-socket` 0.2.11 (enables multiple pg connections via socket server)
  - Per-test-file instance (not shared) to avoid lock contention; reached through standard `pg` client library
  - Implementation: `test/db.ts` - `openTestDb()` creates pglite backend or connects to Docker Postgres
  - Workaround installed: Extended-protocol error filter for pglite-socket issue #958 (fixes premature ReadyForQuery on Parse/Bind/Execute errors)

**File Storage:**
- Local filesystem only: no cloud file storage
- Org metadata loaded from filesystem via SFDX source format (XML)
- Record attachments and documents: not implemented (UNSUPPORTED:attachment-sobject, UNSUPPORTED:document-sobject)

**Caching:**
- None - Postgres is the only source of truth
- In-memory caches: Two map-based caches for Bulk API job state
  - `packages/api/src/bulk/jobs.ts`: `JobInProgressStore` (tracks job state across requests)
  - `packages/api/src/bulk/csv.ts`: `CsvParseCache` (temporary CSV parse results during ingest)

## Authentication & Identity

**Auth Provider:**
- Custom in-process implementation (no external identity provider)
  - `packages/api/src/auth.ts` - SessionStore, LoginResult, token generation
  - Modes: "permissive" (any username, any password) or "list" (hardcoded username/password pairs)
  - Credentials stored in `AuthConfig` (passed at API startup, not persisted)

**Login Flows:**
1. **SOAP Login** (legacy) - POST `/services/Soap/c/<version>/login` with username/password → session ID (token)
2. **OAuth 2 Password Flow** - POST `/services/oauth2/token` with grant_type=password, username, password → access token (bearer)
3. **OAuth 2 Client Credentials** - POST `/services/oauth2/token` with grant_type=client_credentials → access token (logs in as configured user, default: bootstrap admin)
4. **OAuth 2 Refresh Token** - POST `/services/oauth2/token` with grant_type=refresh_token (no-op in orglet; refresh = access)

**Token Format:**
- `{organizationId}!{random-24-byte-base64url}` (e.g., `00Dxx0000000001!mF3Ks...`)
- In-memory SessionStore only; no persistence across server restarts

**User Records:**
- Pulled from the User sObject in the org's Postgres schema
- Fields checked: `Username`, `IsActive`, `ProfileId`, `Id`
- Bootstrap: CLI creates an admin user during `orglet up --import` or org initialization

## Monitoring & Observability

**Error Tracking:**
- No external error tracking service (Sentry, Rollbar, etc.)
- Errors logged via `console.error` (fatal) and `req.log.error` (Fastify logger)
- Request-level errors caught in central error handler (`packages/api/src/server.ts`, `app.setErrorHandler`)

**Logs:**
- `console.log` for normal progress (gated by `--quiet` flag in CLI)
- `console.warn` for warnings prefixed `"warning: "` (e.g., `UNSUPPORTED:*` features)
- `console.error` for fatal startup failures with actionable hints
- Optional structured event stream: `ORGLET_EVENTS=stdout` emits one JSON object per line for each data change event

**Request Logging:**
- Fastify's built-in pino logger: `req.log.warn()` for expected/recoverable gaps (composite rollback, SOSL stubs)
- Disabled by default (`ApiOptions.logger: false`); CLI enables it explicitly with `--verbose`

## CI/CD & Deployment

**Hosting:**
- No deployment target defined; orglet is a local/dev/CI tool only
- GitHub repository: `snorf/orglet` (open source, Apache-2.0)
- Users run `orglet up` locally or in CI/CD pipelines pointing to a self-hosted Postgres

**CI Pipeline:**

GitHub Actions workflows (`.github/workflows/ci.yml`):

1. **test-pglite** (all pushes + PR to main)
   - Runs on ubuntu-latest
   - Installs pnpm via action-setup, Node 22 via nvmrc
   - `pnpm install --frozen-lockfile` → `pnpm build` → `pnpm lint` → `pnpm typecheck:scripts` → `pnpm test`
   - Also runs: `node packages/cli/dist/index.js check --strict --project examples/enterprise` (conformance check without tests)
   - Test environment: embedded pglite (no Docker)

2. **test-postgres** (all pushes + PR to main)
   - Docker service: postgres:16-alpine, env POSTGRES_USER/PASSWORD/DB: orglet, healthcheck
   - Same build steps as test-pglite, but:
   - Env: `ORGLET_DATABASE_URL=postgres://orglet:orglet@localhost:5432/orglet` (via GitHub action service)
   - Test environment: Docker Postgres (maxWorkers=3 to avoid lock table exhaustion)

3. **conformance** (all pushes + PR to main)
   - Matrix: projects = [examples/acme, examples/enterprise]
   - Docker service: postgres:16-alpine
   - Python 3.12 + venv setup
   - Runs all conformance harnesses against orglet instances:
     - `conformance/jsforce/run.sh` (pinned jsforce commit, checks core + bulk2)
     - `conformance/python/run.py` (simple-salesforce SDK)
     - `conformance/cmdt-check` (custom metadata types)
     - `conformance/describe-check` (sObject describe output)
     - `conformance/poly-check` (polymorphic fields)
     - `conformance/rollup-check` (rollup summary fields)
   - Env: PORT=8093, ORG_SCHEMA=conformance_run, CMDT_PORT=8094, CMDT_SCHEMA=conformance_run_cmdt

4. **sigha-sync-check** (all pushes + PR to main)
   - Verifies vendored sigha is reproducible from committed VENDOR.md revision
   - Clones pinned repo/rev, syncs via `scripts/sync-sigha.sh`, diffs `packages/sigha/src` against fresh sync
   - Proves no manual edits were made to vendored code

5. **baseline-gen-check** (all pushes + PR to main)
   - Verifies committed baseline metadata is reproducible from inputs
   - Runs `pnpm baseline:gen`, checks `git diff --exit-code -- packages/metadata/standard` and untracked files
   - Ensures no committed metadata drifts from generation

**Status:** All must pass for PR merge; concurrency: single per ref, in-progress cancelled

## Environment Configuration

**Required env vars (for `orglet up`):**
- `ORGLET_DATABASE_URL` (optional) - Postgres connection string (default: `postgres://orglet:orglet@localhost:5433/orglet`)
  - When unset: CLI falls back to default; tests use embedded pglite

**Optional env vars:**
- `ORGLET_PG_PORT` - host port for docker-compose (default: `5433`)
- `ORGLET_EVENTS` - set to `stdout` to stream data change events as NDJSON
- Node.js standard: `NODE_ENV`, `DEBUG`, etc. (no special usage)

**Secrets location:**
- No secrets committed (`.env*` excluded via `.gitignore`)
- Credentials passed via CLI flags or config file at runtime (`AuthConfig` object for passwords)
- OAuth tokens are ephemeral (in-memory SessionStore)

## Cross-Cutting Concerns

### Data Migration Mode

When `orglet up --import` is used or `EngineOptions.importMode` is set:

- Record IDs and audit timestamps (CreatedDate, LastModifiedDate) are preserved from the source org
- External IDs are honored for upsert operations
- Used for data import workflows and migration testing

### Unsupported Features

Explicitly marked as `UNSUPPORTED:<area>` in error messages and logs:

- Formulas: global functions like `NOW()`, `TODAY()`, `USER()` (context-dependent); entire formula areas not yet implemented
- Field types: some custom types (e.g., rich text); UNSUPPORTED:field-type
- Standard fields: some read-only system fields; UNSUPPORTED:standard-field
- Sobjects: Attachment, Document (file storage); UNSUPPORTED:attachment-sobject
- References: some circular/polymorphic reference patterns; UNSUPPORTED:reference-target
- Schema changes: dropping columns, narrowing fields; UNSUPPORTED:schema-drop, UNSUPPORTED:schema-narrow
- Bulk API: some relationship column configurations; UNSUPPORTED:bulk-relationship-column
- Composite API: no rollback on partial composite failure; UNSUPPORTED:composite-rollback
- SOSL: SOSL search not implemented; UNSUPPORTED:sosl
- Flows, Processes: automation not implemented; UNSUPPORTED:flow

### Data Consistency

- All writes are transactional via Postgres ACID guarantees (BEGIN/COMMIT/ROLLBACK)
- No distributed transactions; single Postgres instance only
- Duplicate key constraints catch duplicate external IDs and unique field violations
- Foreign key constraints enforced (custom lookup failures rejected at Postgres level)

### Order of Execution

DML operations follow Salesforce's order of execution via `TriggerExecutor` (`packages/engine/src/hooks.ts`):

1. Before triggers
2. Validation rules
3. Custom field default values
4. Rollup summary calculations
5. After triggers
6. Workflow rules
7. Process Builder / Flows (not implemented; UNSUPPORTED:process-builder)

Executed per-batch, per-record, in registration order via hook registration pattern.
