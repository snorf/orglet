<objective>
Step A of the two-step landing (Research Pattern 2): a pure, deterministic generator that reproduces the existing 35
objects from the vendored sources plus a mechanically bootstrapped v1.0 pin layer, with the committed files becoming
generator output, and a CI drift gate.

Purpose: SC1 (deterministic, CI drift gate) and SC2 step 1 (no-op against v1.0). Step B (09-06/09-07) only adds fields and
keys on top of a generator that is already proven to reproduce v1.0.
Output: sources.ts, typemap.ts, pipeline.ts, generate.ts, v1-pins.json, keep entries in overrides.json, reformatted
standard/objects/*.json, two test files, CI job.

Planning-time decisions (Claude's discretion, within D-01..D-19 and locked decisions 1-2):
- Generator layout `scripts/gen-baseline/`, run with `tsx`; no workspace package, no new dependency.
- `generate(inputs, { v1Only })`. `v1Only: true` = only objects/fields that exist in v1-pins.json, object JSON in the exact
  v1.0 key set (no keyPrefixSource, no ownerTargets, no featureGated). In this plan `CLI_OPTIONS = { v1Only: true }`; 09-07
  flips it. The v1Only parity test stays forever, so SC2 step 1 is permanently checked.
- v1-pins.json lists **every** v1.0 object and field (empty `{}` when nothing differs), so the generator learns the v1.0
  inventory from its own inputs and never reads the test fixture; only `--bootstrap-pins` and the tests read the fixture.
- Pin value `null` means "this key is absent in v1.0" (delete the derived key).
- Object-level v1.0 facts (label, labelPlural, createable, updateable, deletable, undeletable, queryable, searchable,
  hasOwner) are fully pinned in `pins.<Object>.object`: neither source states them. keyPrefix comes from overrides (D-07).
- Precedence: overrides.json > v1-pins.json > source-derived > type defaults (Research Pattern 6).
- Source conflicts (D-03, discretion): the generator **aborts** on any unresolved conflict (Research recommendation). On a
  v1.0 field a pin settles it (provenance `v1.0`); the bootstrap therefore pins every fact on which the sources disagree.
- Compared facts for conflicts: type (after mapping), createable, updateable, nillable, defaultedOnCreate, referenceTo (as
  a sorted set), relationshipName, length (only when both sources state one). Labels are not compared (the PDF has none).
- Fields absent from both sources but in v1.0 (Research: `Account.Tier`) and objects absent from both
  (`BusinessProcess`) are kept only with an overrides.json `keep` / `keepObject` entry with the reason text
  "present in v1.0, absent from sources" (D-06); the bootstrap writes those entries. Without one the generator aborts.
- Reformat (locked decision 1): the 35 files change whitespace only; the commit message says so, and the test proves
  parsed equality with the fixture.
</objective>

| multipicklist | MultiselectPicklist | same |
| boolean | Checkbox | |
| int | Number, precision 18, scale 0 | guessed |
| double | Number, precision 18, scale 6; names ending Latitude/Longitude: 18,15 | guessed |
| currency | Currency 18,2 | |
| percent | Percent 5,2 | guessed |
| date / datetime / time | Date / DateTime / Time | |
| phone / url / email | Phone / Url / Email | length per precedence |
| reference | Lookup (MasterDetail when the PDF relationshipType is master-detail) | referenceTo from refers_to / refersTo, split on ",", trimmed, sorted |
| address | Address, createable false, updateable false | parts get compoundFieldName (below) |
| id | skip (system field; loader adds) | |
| junctionidlist, base64, anytype, complexvalue, location | skip + report `UNSUPPORTED:field-type` (existing area, reused per CLAUDE.md; message names the standard field and the source type) | not physical columns |

Length precedence for Text/Phone/Url/Email/TextArea/LongTextArea: overrides > pins > sf-skills `field_reference[name].length`
(only when the source type is string|phone|url|email|textarea; parse the string) > PDF `maxLength` > 255 marked `guessed`
(D-05). For LongTextArea prefer PDF `maxLength` over `field_reference` (UI length quirk). Length > 131072 is reported.

Property tokens -> flags (absence = false; write a flag only when it differs from the loader default):
`Create`->createable, `Update`->updateable, `Nillable`->nillable (write only false values of these three);
`Defaulted on create`->defaultedOnCreate, `Unique`->unique, `Idlookup`/`ID lookup`->idLookup, `Name Field`->nameField,
`Case Sensitive`->caseSensitive, `External ID`->externalId (write only true values). Ignore Filter/Sort/Group/Aggregatable/
Query/Retrieve/Delete (not in the v1 shape). Missing sf-skills `properties` = no flag facts from sf-skills (use PDF).

Compound parts: for each `address` field `XAddress`, fields named `X` + one of Street, City, State, PostalCode, Country,
Latitude, Longitude, GeocodeAccuracy, StateCode, CountryCode get `compoundFieldName: "XAddress"`.

Label: `field_reference[name].field_label`, else humanise the API name (split camel case, drop trailing `Id` -> " ID"),
