<objective>
Make `migrate()` the upgrade safety net: an FK that existing rows would violate becomes an
`UNSUPPORTED:schema-fk` warning instead of an aborted `orglet up` (D-01..D-03), and a second run on
an up-to-date database executes no `CREATE INDEX` / `CREATE SEQUENCE` (D-04).

Purpose: success criteria 2 and 3 (MIGR-02, MIGR-04). The upgrade test in 08-07 asserts on exactly
these behaviours through `MigrateResult.statements` and `MigrateResult.warnings`.

Planning-time decisions (Claude's discretion per CONTEXT, do not relitigate):
- Sequences get the same catalog-skip treatment as indexes (`pg_sequences`), so `statements` contains
  no `CREATE ...` except `CREATE SCHEMA IF NOT EXISTS` on a second run. `CREATE SCHEMA IF NOT EXISTS`
  stays (research Open Question 3: criterion names only CREATE INDEX).
- `IF NOT EXISTS` stays in `indexSql`/`sequenceSql` (belt-and-braces); it is not the mechanism.
- The `schema-fk` warning carries a one-line fix hint (exact text below).
- The try/catch around ADD CONSTRAINT and `isPgForeignKeyViolation` are removed: a failed statement
  aborts the whole Postgres transaction, so catch-and-continue is impossible; the pre-check is the mechanism.
- `NOT VALID` is never used (Phase 3 decision, D-01). Nothing in `_orglet` remembers the skip (D-02).

Output: updated `migrate.ts`, rewritten FK test and extended idempotency test in `migrate.test.ts`,
one new backend check in `pglite-compat.test.ts`.
</objective>
