Facts verified at planning time (research probes on Fastify 5.12.5 in this repo):
- A static trailing segment `/services/data/v:version/sobjects/:type/:id/VersionData` wins over `/:type/:field/:value`;
  `/Account/Name/Acme` and `/Account/VersionData/x` still reach the external-id route. Registration order is irrelevant.
- A content-type parser that calls `done(Object.assign(new Error(..), { statusCode, errorCode }), undefined)` reaches
  `setErrorHandler` with those properties. Without a multipart parser Fastify answers 415 FST_ERR_CTP_INVALID_MEDIA_TYPE,
  which the handler maps to UNSUPPORTED_MEDIA_TYPE today.
- A JSON body above `bodyLimit` (64 MiB, server.ts:88) raises statusCode 413 (FST_ERR_CTP_BODY_TOO_LARGE); the handler has no
  branch for it and answers 500 UNKNOWN_EXCEPTION today.
- `onSend` (server.ts) sets a JSON content-type only when none is set; a stream payload passes through.
- jsforce sends multipart only with `options.multipartFileFields` (connection.ts:1002-1023), with Content-Type `multipart/form-data; boundary=...`.

Decisions written into this plan:
- Multipart status: 415 with `apiError("UNSUPPORTED", "UNSUPPORTED:content-multipart multipart request bodies are not supported yet; send VersionData as base64 in a JSON body")`.
  Detection by Content-Type only (`/^multipart\//i`), never by part names; the body is never read.
- Oversize: HTTP 413, errorCode `MAXIMUM_SIZE_OF_DOCUMENT` for both the engine cap (`Errors.contentTooLarge`, plan 15-01) and Fastify's bodyLimit
  (`UNSUPPORTED:content-size request body exceeds the 64 MiB limit`). No env var (D-05).
- Content-Length: the BlobStore's `size` is the authority (a header promising more bytes than the stream delivers hangs the
  client). This deviates from D-06's literal "from ContentSize": when ContentSize differs from the stored size, the download still
  answers with the stored size and logs one `blob-size` diagnostic per version Id. Say so in the SUMMARY.
- Diagnostics are `req.log.warn` lines, emitted once per process per `<area>:<versionId>` (a Set on the route closure), areas
  `blob-missing`, `blob-checksum`, `blob-size`; shape `req.log.warn({ area, id, expected, actual }, "<area> ContentVersion <id>: ...")`.
  They are integrity findings, not unimplemented features, so they carry no `UNSUPPORTED:` prefix. Never log content bytes or filenames.
- Content-Disposition: `attachment` plus `filename="<ascii>"; filename*=UTF-8''<percent-encoded>` from the basename of PathOnClient
  (split on `/` and `\`); the ascii form keeps only printable ASCII except `"` and `\`; if the basename is empty, send bare `attachment`.
- A soft-deleted ContentVersion answers 404 (retrieve excludes deleted rows), consistent with record GET.
- The URL is returned for every live version even when no bytes are stored; the download is what answers 404.
- The "large upload" memory test runs on Postgres only (`skip(usingPglite, ...)`, the existing pattern): pglite runs inside the test
  process, so its WASM memory would dominate RSS and make the bound meaningless.
