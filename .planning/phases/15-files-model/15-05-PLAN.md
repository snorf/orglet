<objective>
Make `ContentVersion.ContentDocumentId` NOT NULL in storage (D-01) and teach `migrate()` to reconcile nullability the
Phase 8 way (D-02): a planned NOT NULL column that is nullable in the database gets `SET NOT NULL` when no row violates
it, and otherwise is skipped with one counted `UNSUPPORTED:schema-notnull` warning per column, re-evaluated on every
`up`; migrate never rewrites rows. Prove it on a populated v1.1 database (roadmap note).

Purpose: describe (`nillable: false`, plan 15-03) and storage say the same thing without ever touching user data.
Output: columns/ddl/migrate changes, migrate unit cases, a frozen v1.1 baseline fixture and upgrade-v11.test.ts.
</objective>

Decisions written into this plan:
- Area name: `schema-notnull` (sibling of `schema-fk`; `schema-narrow` is about type width and would mislead).
- Rule location: an explicit set in columns.ts, keyed `Object.Field`, so the rule can never generalise to
  "nillable:false implies NOT NULL". `columnFor` gains a required second parameter `objectName: string`.
- The reconcile step is generic (any planned NOT NULL column that is nullable in the database), because a nullable column
  the plan wants NOT NULL is drift whatever caused it; `--force` does not change it (migrate never rewrites data).
- Message: `column <table>.<column> holds <n> row(s) with NULL; NOT NULL not applied; correct them and run orglet up again`.
