Planning-time decisions (do not relitigate):
- delete/undelete reuse 05-05's `withRollups` replay loop and `recomputeRollups` with kinds "delete"/"undelete"
  (trigger: the old FK). The body of the wrapper is "cascade + setDeleted + after-hooks" (delete) and
  "setDeleted(false) + cascade + after-hooks" (undelete); live ids are recomputed inside the body so a replay
  only touches survivors.
- Cascade safety: `deleteBatch` gets a `deleting: ReadonlySet<string>` parameter (default `NO_IDS`); the recursive
  cascade call passes `new Set([...deleting, ...ids])`, and recompute skips parent ids in that set, so a parent
  being deleted up the stack is never recomputed, rule-checked or hooked. `undeleteBatch` needs no such set (it
  makes the parent live first, so the inner recompute is correct; the outer one is idempotent).
- No primary Salesforce quote states the reparent and undelete triggers (ROADMAP research flag; Help 000391766
  covers only manual recalculation). They are implemented as required by ROLL-04 and recorded in the SUMMARY so
  /gsd:verify-work notes the sourcing gap.
- Filter-operator integration uses an in-memory schema (phase 4 D-13 pattern): acme's SourceProject plus two
  extra Milestone__c fields and extra Summary fields on Project__c, in a second org schema in the same test file.
  Dates in tests are fixed literals, never "today".
