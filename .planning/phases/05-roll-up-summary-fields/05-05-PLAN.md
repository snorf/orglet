<objective>
Recompute roll-ups in the app-side save pipeline for insert/update/upsert, including reparent and
filter-only changes, with the parent's rules and hooks (ROLL-04 insert/update half, ROLL-05), correct
partial-success attribution (D-03, ROADMAP criterion 3), upward chain propagation (ROLL-06
mechanism), D-04 defaults and D-09 import behaviour. Delete/undelete wiring and the remaining
chain/SOQL tests are plan 05-06.

Planning-time decisions (do not relitigate; they implement the CONTEXT decisions in a different
mechanism with the same behaviour):
- D-03 failure attribution uses a batch savepoint with a bounded replay loop (05-RESEARCH Pattern 2):
  `SAVEPOINT rollup_batch`; write loop (existing per-record `SAVEPOINT rec`) + child after-hooks + recompute;
  if the recompute marked any child newly failed: `ROLLBACK TO` + `RELEASE` and replay with the survivors,
  else `RELEASE`. Reason: a per-parent nested savepoint alone cannot undo child writes whose savepoints were
  already released; replaying from the surviving state makes every committed parent value reflect exactly
  the committed children (the reparent case where the old parent fails and the new one already counted the
  child). Terminates: each repeated pass fails at least one more child; guard throws after `work.length + 1` passes.
  The per-parent nested savepoint from D-03 is kept (`SAVEPOINT rollup_parent` around the parent UPDATE and its
  after-hooks). Ids, auto-numbers, defaults and before-hook results are computed before the loop and are not
  recomputed on replay; after-hooks run again for survivors (inert today; DB effects of the failed pass were rolled back).
- Recompute is SELECT-first (`rollupSelectSql` from 05-03), then per changed parent: before-hooks, fold hook
  changes into `changes` exactly like saveBatch, validation rules, `store.update` with only the changed columns
  (plus hook changes), after-hooks. This honours D-03's "one batched aggregate statement per roll-up field set"
  while letting the parent's rules see the prospective row (D-01).
- Blame set (D-03 literal): every live child in the batch whose old or new FK points at the failed parent,
  whether or not that child triggered the recompute. Child error: `saveError(parentError.statusCode, parentError.message)`
  (no `fields`: the parent's errorDisplayField names a parent field), which for a rule is
  FIELD_CUSTOM_VALIDATION_EXCEPTION with the parent rule's message.
- Trigger rule per child work: insert -> new FK; update -> old and new FK when they differ (reparent), else the
  FK when any watched field (FK, summarized field, filter fields, valueFields) is a key of `changes`
  (over-approximation; recompute is idempotent); delete/undelete -> old FK (wired in 05-06).
- Skip the parent save when no roll-up value changed (no hooks, no rules; 05-RESEARCH Pitfall 10, LOW).
  Do not stamp LastModifiedDate/LastModifiedById/SystemModstamp on the parent (LOW, asserted by a test).
- No ChangeBus events for parent recompute updates (internal event stream; recorded as a known limitation).
- Chains: after a parent is written, its own bindings as a child (`registry.forChild(parent)`) decide the next
  level with the same trigger rule (kind "update" on the parent work); blame carries through to the original
  children. Depth guard: throw `Error("roll-up recompute on <Child> did not settle after 16 levels")`.
- Concurrency hardening (parent row locks) is out of scope; single-tenant, low-concurrency tool.
- Skip the replay wrapper entirely in import mode and for objects with no bindings, so SQL for every other
  object is unchanged.

Output: `packages/engine/src/rollups.ts`, engine.ts changes, `packages/engine/src/rollups.test.ts`.

    ```typescript
    /**
     * Runs a batch's writes and after-hooks together with the roll-up recompute under one savepoint. When a parent
     * refuses (rule or hook), the children it blames now carry errors: roll the batch back and replay the survivors,
     * so committed parents only ever reflect committed children (D-03).
     */
    private async withRollups(client: PoolClient, obj: SObjectDef, size: number, body: () => Promise<void>, recompute: () => Promise<number>): Promise<void> {
      if (this.importMode || this.rollups.forChild(obj).length === 0) return body();
      for (let pass = 0; ; pass++) {
        if (pass > size) throw new Error(`roll-up replay on ${obj.name} did not converge`);
        await client.query("SAVEPOINT rollup_batch");
        await body();
        if ((await recompute()) === 0) {
          await client.query("RELEASE SAVEPOINT rollup_batch");
          return;
        }
        await client.query("ROLLBACK TO SAVEPOINT rollup_batch");
        await client.query("RELEASE SAVEPOINT rollup_batch");
      }
    }
    ```
